# 360度評価システム バックエンドAPI

「360度評価システム 要件定義書 v1.6」「360度評価システム データ定義書 v1.1」に基づく実装です。
このリポジトリには2つの独立した Google Apps Script プロジェクトが含まれます。

| ディレクトリ | 役割 | 実行主体 |
|---|---|---|
| `src/` | 360度評価API本体(Web アプリ)。ログイン認証・マスタ取得・評価送信 | 360度評価システム用の実行アカウント |
| `hr-sync/` | F-11: 人事原本(社員名簿)→評価専用マスタへの同期スクリプト | 人事担当者自身のアカウント(人事原本にバインド) |

### 2つのスプレッドシートに分離される(要件定義書 5.1)

マイナンバー等の機微情報を含む**人事原本(社員名簿)**と、360度評価APIが読み書きする
**評価専用マスタ**(社員マスタ抜粋／部門マスタ／部署マスタ／評価期間マスタ／評価結果ログの5タブ)はファイルレベルで分離します。

- `src/` の Web アプリは **評価専用マスタのみ** にアクセスし、人事原本への読み取り権限は一切持たない
- 人事原本 → 評価専用マスタの反映は `hr-sync/` が人事担当者の権限で行う(社員番号・氏名・メールアドレス・部署・代表フラグ・有効フラグの5項目。パスワードのみ評価専用マスタ側で管理し、新規社員の初回発行時のみ同期スクリプトが払い出す)
- 人事原本(既存の「社員一覧」)は今回一切変更しない。評価専用マスタは新規に別スプレッドシートとして作成する
- 人事原本には「部署」シート(部門・部署コード・部署の対応表)があり、これが部署の一覧の正となる。`hr-sync/` はこのシートを直接参照するため、事業所名の対応表を手動で二重管理する必要はない

デスクトップアプリは `src/` の action を呼び出すだけで、スプレッドシートやDriveに直接アクセスすることはありません。デスクトップアプリの画面コード自体の自動更新チェック(`getAppUpdate`)もこのAPI経由で行います(`desktop-app/README.md`参照)。

### 部門・部署・評価基準の階層

「部門」(例: 児童発達支援、役員)の下に複数の「部署」(例: Campo台之郷、Campo大原、代表)がぶら下がる。
評価基準(大項目2×小項目5+自由記述2)は**部門マスタにデフォルトを1セット**持たせ、**部署マスタでは同じ列を上書き用**として持つ。
部署マスタ側のセルが空欄ならば部門マスタのデフォルト値を使う(部署ごとに個別の基準にしたい場合だけ埋める)。

- F-02(評価対象者一覧)・二重送信防止などの「同じグループかどうか」の判定は、部門ではなく**部署**の一致で行う(社員マスタ.部署が主キー)
- 代表フラグは `hr-sync/` が「部署」シートから自動算出する(部署の部門が代表用の部門名(既定「役員」)と一致する社員を代表フラグ=TRUEとする)。評価専用マスタ側で手動設定する必要はなく、同期のたびに上書きされる
- 代表(荻野氏)は評価する側にはならず、全社員から代表向け簡易評価(F-10: 自由記述のみ)を受ける側のまま。ただし代表自身がログインして `getMaster` を呼ぶこともあるため、部署マスタ・部門マスタには代表の部署(既定「代表」/部門「役員」)の行も用意しておくこと

## 提供するAPI(action)

いずれも単一の Web アプリ URL(`.../exec`)に対して **POST + JSON ボディ** でリクエストします。
`action` フィールドで呼び出す処理を切り替えます。

| action | 説明 |
|---|---|
| `login` | 社員番号・パスワードでログイン認証し、トークンを発行する |
| `getMaster` | ログイン中の社員に紐づく部署の評価項目・評価期間一覧・評価対象者一覧を取得する |
| `submitEvaluation` | 評価結果ログへ1件の評価を送信する |
| `getAppUpdate` | デスクトップアプリの画面コードの最新バージョン・内容を返す(認証不要。詳細は`desktop-app/README.md`) |
| `ping` | 疎通確認(GETでも可) |

パスワードやトークンをURLに残さないため、`login` / `getMaster` / `submitEvaluation` は **GET非対応**
です(GETは`ping`のみ受け付けます)。

### 共通レスポンス形式

成功時:
```json
{ "success": true, ... }
```

失敗時:
```json
{ "success": false, "error": { "code": "VALIDATION_ERROR", "message": "..." } }
```

### エラーコード一覧

| code | 意味 |
|---|---|
| `VALIDATION_ERROR` | 入力値不正・必須項目不足 |
| `INVALID_CREDENTIALS` | 社員番号またはパスワードが誤り、または退職者(有効フラグ=FALSE) |
| `ACCOUNT_LOCKED` | ログイン試行回数の上限に達し、一時的にロック中(要件定義書 7.1) |
| `AUTH_ERROR` | トークンが不正・期限切れ・対象社員が無効化された |
| `PERIOD_CLOSED` | 指定した評価期間が受付中でない |
| `DUPLICATE_SUBMISSION` | 同一(評価者, 被評価者, 期間)の評価が送信済み(要 overwrite 確認) |
| `DATA_ERROR` | マスタ間の参照整合性エラー(例: 部署マスタ・部門マスタに該当行がない) |
| `CONFIG_ERROR` | スクリプトプロパティ・シート未設定などサーバー設定不備 |
| `UNKNOWN_ACTION` | 不明な action |
| `METHOD_NOT_ALLOWED` | GETで認証系APIを呼んだ場合など |
| `INTERNAL_ERROR` | 想定外のサーバーエラー |

## 1. ログイン認証 `login`

**リクエスト**
```json
{ "action": "login", "employeeId": "100001", "password": "xxxxxxxx" }
```

**レスポンス**
```json
{
  "success": true,
  "token": "eyJzdWIiOiIxMDAwMDEi...ペイロード.署名",
  "expiresInMinutes": 480,
  "employee": {
    "employeeId": "100001",
    "name": "井出玲歌",
    "unit": "Campo台之郷",
    "isRepresentative": false
  }
}
```

- 社員マスタの社員番号・パスワードを完全一致で照合します。
- 有効フラグ=FALSE(退職者)は存在しない社員番号と同じエラーメッセージを返し、在籍有無を推測させません。
- `token` は社員番号+有効期限をスクリプトプロパティ`TOKEN_SECRET`でHMAC-SHA256署名したものです。
  以降の `getMaster` / `submitEvaluation` はこの `token` を必須パラメータとして渡します。
- 総当たり対策(要件定義書 7.1): 同一社員番号で認証に**5回連続失敗**すると**15分間**ロックされ、
  ロック中は資格情報を照合せず即座に `ACCOUNT_LOCKED` を返します。ロックは`CacheService`(スクリプト共有キャッシュ)
  で管理し、認証成功時にリセットされます。閾値は`Constants.js`の`LOGIN_MAX_ATTEMPTS`等で変更可能です。

## 2. マスタ取得 `getMaster`

**リクエスト**
```json
{ "action": "getMaster", "token": "..." }
```

**レスポンス**
```json
{
  "success": true,
  "employee": { "employeeId": "100001", "name": "井出玲歌", "unit": "Campo台之郷", "isRepresentative": false },
  "evaluationItems": {
    "department": "児童発達支援",
    "unit": "Campo台之郷",
    "section1": { "title": "基本理念", "items": ["...", "...", "...", "...", "..."] },
    "section2": { "title": "チーム協働・褒め合う文化", "items": ["...", "...", "...", "...", "..."] },
    "freeText1Label": "基本理念について良かったこと",
    "freeText2Label": "チーム協働について良かったこと"
  },
  "periods": [
    {
      "periodId": "2026-summer",
      "periodName": "2026年夏季賞与向け評価",
      "startDate": "2026/05/01",
      "endDate": "2026/05/31",
      "status": "実施中",
      "isOpen": true
    }
  ],
  "targets": [
    { "employeeId": "100002", "name": "...", "unit": "Campo台之郷", "isRepresentative": false }
  ]
}
```

- `evaluationItems` はログイン社員の部署が属する部門マスタの行(デフォルト)を土台に、部署マスタ側で値が入っている列だけを上書きして組み立てます(空欄の列は部門マスタの値をそのまま使用)。
- `periods` は評価期間マスタの全件。`isOpen` は「実施ステータス=実施中」かつ「本日が受付開始日〜受付終了日の範囲内」の両方を満たす場合に `true`。
- `targets`(評価対象者一覧, F-02)は「自分と同じ部署の在籍社員」+「部署を問わず代表フラグ=TRUEの在籍社員」で、自分自身は除外します。

## 3. 評価送信 `submitEvaluation`

**通常評価のリクエスト例**
```json
{
  "action": "submitEvaluation",
  "token": "...",
  "evaluateeId": "100002",
  "periodId": "2026-summer",
  "evaluationType": "通常",
  "scores1": [5, 4, 5, 3, 4],
  "scores2": [4, 4, 5, 5, 4],
  "freeText1": "基本理念についての自由記述",
  "freeText2": "チーム協働についての自由記述"
}
```

**代表向け簡易評価のリクエスト例(F-10)**
```json
{
  "action": "submitEvaluation",
  "token": "...",
  "evaluateeId": "999999",
  "periodId": "2026-summer",
  "evaluationType": "代表",
  "freeText1": "良いところ"
}
```

**レスポンス**
```json
{ "success": true, "logId": "xxxxxxxx-xxxx-...", "submittedAt": "2026-08-16T09:00:00.000Z", "overwritten": false }
```

### バリデーション・業務ルール

- `evaluationType` は `通常` / `代表` のいずれか。
- 自分自身を評価対象にはできません。
- 指定した `periodId` が存在し、かつ受付中(`isOpen`)である必要があります。そうでなければ `PERIOD_CLOSED`。
- 被評価者は在籍中(有効フラグ=TRUE)である必要があります。
  - `通常`評価: 評価者と同じ部署の社員、または代表フラグ=TRUEの社員のみ指定可能(F-02の対象者一覧と整合)。
  - `代表`評価: 代表フラグ=TRUEの社員のみ指定可能。
- `通常`評価は `scores1` / `scores2` (各5要素・1〜5の整数)が必須。範囲外の値は `VALIDATION_ERROR` でエラーとします(7章の入力規則)。
- `代表`評価はスコア無し、自由記述2は使用しません(送信されても無視して空欄で記録)。
- **二重送信防止**: (評価者社員番号, 被評価者社員番号, 期間ID)が既に存在する場合、デフォルトでは `DUPLICATE_SUBMISSION` エラーを返します。ユーザーに上書き確認をとった上で `overwrite: true` を付けて再送信すると、既存行を新しい内容で上書きします(新規行の追加ではなく更新)。
- 判定〜書き込みは `LockService` でロックし、同時送信による二重登録を防ぎます。

## セットアップ手順

### 1. 評価専用マスタ(新規スプレッドシート)の準備

**人事原本(既存の社員一覧)とは別に、新しいスプレッドシートを1つ作成**し、以下の5シートを用意して、
1行目に以下のヘッダーを入力してください(列の順序は問いません)。既存の人事原本は変更しません。

> 下記の構成であらかじめ作成済みのスプレッドシートを用意しています:
> https://docs.google.com/spreadsheets/d/1wVcc7QpQwgAp-bf5tLKKl2dbn2e2qXBhiGaH0Kqm6sk/edit
> 人事原本の「部署」シートから部門(児童発達支援・役員)・部署(Campo台之郷・Campo大原・代表)を
> 転記済みです。評価基準(大項目・小項目・自由記述ラベル)は未確定のため空欄のままにしてあるので、
> 内容が決まり次第「部門マスタ」タブに入力してください(部署ごとに変えたい場合のみ「部署マスタ」タブ側に入力)。

**社員マスタ**
```
社員番号 | 氏名 | パスワード | メールアドレス | 部署 | 代表フラグ | 有効フラグ
```

**部門マスタ**(部門ごとの評価基準デフォルト。全列必須)
```
部門名 | 大項目1名 | 小項目1-1 | 小項目1-2 | 小項目1-3 | 小項目1-4 | 小項目1-5 |
大項目2名 | 小項目2-1 | 小項目2-2 | 小項目2-3 | 小項目2-4 | 小項目2-5 | 自由記述1ラベル | 自由記述2ラベル
```
例: `児童発達支援` 行、`役員` 行(代表用)など、人事原本の「部署」シートに出てくる部門をすべて用意する。

**部署マスタ**(部門マスタの列を部署単位で上書きしたい場合だけ入力。空欄は部門マスタの値を継承)
```
部署名 | 部門 | 大項目1名 | 小項目1-1 | 小項目1-2 | 小項目1-3 | 小項目1-4 | 小項目1-5 |
大項目2名 | 小項目2-1 | 小項目2-2 | 小項目2-3 | 小項目2-4 | 小項目2-5 | 自由記述1ラベル | 自由記述2ラベル
```
`部署名`は社員マスタの「部署」、`部門`は部門マスタの「部門名」と完全一致させる。
人事原本の「部署」シートにある部署(Campo台之郷・Campo大原・代表 等)をすべて行として用意する(基準を部門と共通にする場合は評価基準列を空欄のままにする)。

**評価期間マスタ**
```
期間ID | 期間名 | 受付開始日 | 受付終了日 | 実施ステータス
```

**評価結果ログ**
```
ログID | 評価者社員番号 | 被評価者社員番号 | 期間ID | 評価種別 |
小項目1-1スコア | 小項目1-2スコア | 小項目1-3スコア | 小項目1-4スコア | 小項目1-5スコア |
小項目2-1スコア | 小項目2-2スコア | 小項目2-3スコア | 小項目2-4スコア | 小項目2-5スコア |
自由記述1 | 自由記述2 | 送信日時
```

- 社員番号列・期間ID列は「書式なしテキスト」に設定し、先頭0が消えないようにしてください。

### 2. `src/`(360度評価API)のデプロイ (clasp)

```bash
npm install
npx clasp login

# 新規スタンドアロンGASプロジェクトとして作成する場合(リポジトリ直下で実行)
npx clasp create --type webapp --title "360度評価システム API" --rootDir src

# 生成された .clasp.json の scriptId を確認し、必要なら .clasp.json.example を参考に調整
npx clasp push
npx clasp deploy
```

デプロイ後、Web アプリのURL(`https://script.google.com/macros/s/xxxxx/exec`)を控えます。

### 3. `src/` のスクリプトプロパティの設定

Apps Script エディタの「プロジェクトの設定」→「スクリプト プロパティ」で以下を設定します。

| キー | 値 | 必須 |
|---|---|---|
| `SPREADSHEET_ID` | 評価専用マスタ(手順1で作成したスプレッドシート)のID | 必須(スタンドアロンスクリプトのため) |
| `TOKEN_SECRET` | ログイントークン署名用のランダムな秘密文字列(32文字以上推奨) | 必須 |
| `APP_UPDATE_DRIVE_FILE_ID` | デスクトップアプリの画面コード更新パッチ用Driveファイルのファイル ID(`1XXfpI3lEuyUPJ1Yu0EcAzD-zc7IdKL1_` を初期値として作成済み) | `getAppUpdate` action(デスクトップアプリの自動更新)を使う場合は必須。使わないなら未設定でよい |

```bash
curl -s "https://script.google.com/macros/s/xxxxx/exec?action=ping"

curl -s -X POST "https://script.google.com/macros/s/xxxxx/exec" \
```

### 5. `hr-sync/`(F-11 人事原本→評価専用マスタ同期)のセットアップ

こちらは人事原本(社員名簿)に**コンテナバインド**するスクリプトです(Web アプリではありません)。
人事担当者自身が人事原本のApps Scriptエディタから設定し、人事担当者のアカウント権限で実行されます。

```bash
# 人事原本のスプレッドシートを開き、拡張機能 > Apps Script でエディタを開く
# エディタのプロジェクト設定で任意の scriptId を控え、hr-sync/.clasp.json を用意する
cd hr-sync
npx clasp push
```

「プロジェクトの設定」→「スクリプト プロパティ」で以下を設定します。

| キー | 値 | 必須 |
|---|---|---|
| `EVAL_MASTER_SPREADSHEET_ID` | 評価専用マスタ(手順1で作成したスプレッドシート)のID | 必須 |
| `SOURCE_SHEET_NAME` | 人事原本内の社員一覧シート名 | 省略時 `シート1` |
| `SOURCE_DEPARTMENT_SHEET_NAME` | 人事原本内の「部署」シート名(部門・部署コード・部署の対応表) | 省略時 `部署` |
| `REPRESENTATIVE_DEPARTMENT_NAME` | 代表とみなす部門名。「部署」シートでこの部門に属する部署の社員は代表フラグ=TRUEとして同期する | 省略時 `役員` |
| `RESIGNED_DEPARTMENT_NAME` | 退職者用の部門名。「部署」シートでこの部門に属する部署の社員は有効フラグ=FALSEとして同期する | 省略時 `退職` |
| `SYNC_DRY_RUN` | `true` にすると実際の書き込み・メール送信を行わずに件数だけ確認できる | 任意(初回動作確認時に推奨) |

部署の判定は人事原本の「部署」シート(部門・部署コード・部署の3列)を直接参照します。事業所名の対応表を
スクリプトプロパティ側で手動管理する必要はありません。社員一覧側は「所属」列(所属履歴グループ内の現在値。
コード無しで部署名がそのまま入っている列)を参照します。

設定後、人事原本のスプレッドシートを開き直すとメニューバーに「360度評価」→「評価用マスタへ反映」が追加されます。
人事担当者が社員一覧または部署一覧を更新した後、このメニューを押すと同期が実行されます(自動巡回トリガーは設けません)。

- 既存社員: 氏名・メールアドレス・部署・代表フラグ・有効フラグを更新します。パスワードのみ既存値を維持します
- 新規社員: 評価専用マスタに行を追加し、パスワードを自動発行してメールアドレス宛に送付します(F-08)
- 「所属」列の値が「部署」シートに無い社員はスキップされ、完了時のダイアログに一覧表示されます

## セキュリティ・実装上の注意

- パスワードはデータ定義書の仕様通り「本部発行の固定パスワード」を社員マスタに平文で保持する前提で実装しています。将来的にハッシュ化(例: `Utilities.computeDigest`によるSHA-256+ソルト)へ移行する場合は `AuthService.login` の比較ロジックのみ差し替えれば済む構成にしています。
- Web アプリは常にHTTPS経由でのみ提供されるため、通信経路上の盗聴リスクはGASの標準機能で担保されます。
- トークンは8時間で失効します(`Constants.js`の`TOKEN_TTL_MINUTES`で変更可能)。トークン検証時は毎回社員マスタを再照会し、ログイン後に有効フラグがFALSEへ変更された社員のアクセスも遮断します。
- ブラウザ(SPA等)から呼び出す場合、`Content-Type: application/json` はCORSプリフライトの対象になりGASでは正しく扱えないことがあります。デスクトップアプリ(Node/Electron等のサーバーサイドHTTPクライアント)からの利用を前提としています。
- `hr-sync/` は人事原本(マイナンバー等の機微情報を含む)にバインドし、人事担当者自身の権限で実行されます。360度評価API(`src/`)の実行アカウントには人事原本への読み取り権限を一切付与しないでください(要件定義書 5.1・7.1)。
- `hr-sync/` は評価専用マスタの「社員マスタ」シートに対して、氏名・メールアドレス・部署・代表フラグ・有効フラグの更新とパスワード自動発行(新規行のみ)を行います。パスワード列のみ既存社員に対して一切書き換えません。代表フラグはデータ定義書v1.1の「本部が手動設定」から変更し、「部署」シート(部門=代表用の部門名)を根拠に同期のたびに自動算出・上書きします。
